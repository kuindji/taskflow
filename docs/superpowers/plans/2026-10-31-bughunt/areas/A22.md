## Rounds

### Round 1 (2026-11-01): 2 findings, 2 confirmed

- R1-1 confirmed: with a task's detail open, selecting another task in the
  sidebar updated the view in place but its edit callbacks stayed bound to
  the first task's id, so a title/description/attribute/pin/archive edit
  hit the wrong task. The detail now reopens when the task changes.
  Commit: 62800bd2.
- R1-2 confirmed: sidebar navigation (arrow keys and mouse) chained
  `loadOwnerProducts()` without a catch; offline, the guard rejects the
  flow-run and schedule loads and the unhandled rejection exited the TUI.
  Both chains now swallow the error like the other reload paths.
  Commit: 62800bd2.

### Round 2 (2026-11-01): 4 findings, 4 confirmed

- R2-1 confirmed: opening an unread notification offline left the
  `markRead()` rejection unhandled and the TUI exited. The read update now
  swallows its error like the other offline paths. Commit: e78420ce.
- R2-2 confirmed: a successful flow or action delete never cleared the
  library's pending state, so "Working..." stayed and every key (including
  `q`) was ignored. Commit: e78420ce.
- R2-3 confirmed: function keys F1–F12 reached sessions as nothing; key
  normalization cleared their `code`, and OpenTUI's encoder needs a physical
  key name. They now map to `F<n>`. Commit: e78420ce.
- R2-4 confirmed: `selectOwner` (machine selection restore, project add)
  and notification navigation replaced the owner before `refreshRows`, which
  then saw no owner change and skipped loading flows, schedules and logs, so
  a restored task's paused flow run did not show. `refreshRows` now takes the
  previous owner from those callers. Commit: e78420ce.

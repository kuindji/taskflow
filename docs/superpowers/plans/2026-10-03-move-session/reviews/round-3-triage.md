# Round 3 triage

Each finding was checked against the code on main (18f4c540).

1. **File links moved into Master fail with a CLI editor.** Confirmed, major. Activation forwards only `taskId` and `projectId` (`terminal-link-provider.ts:283`). For Master, `openFileInApp` (`open-file.ts:63`) then calls `createSession({})`, which throws `Either taskId, projectId, or master is required` (`session-store.ts:175`) into a `void`ed promise, so nothing opens. Master terminals already hit this before the feature, but the plan claims that links follow a session into Master, and manual check 8 depends on it. The pane-key part is also confirmed: `openFileInApp` never passes `targetWorkspaceKey`, so a right-pane link would open its editor in the left pane once `sessionWorkspace` returns `:right` keys. Fixed in Section 6: `sessionWorkspace` returns a `SessionOwnerRef` (`{ master: true }` for Master), activation passes it through, `openFileInApp` takes a `SessionOwnerRef` and forwards `workspaceKey` as `targetWorkspaceKey`. New `open-file.test.ts` runs against `startTestServer` with a detected CLI editor. Manual check 8 now covers a CLI editor too.
2. **Master rollback tests don't guard cache ordering.** Confirmed, minor. The Section 3 spies replace `addMasterSession`/`removeMasterSession` entirely, so the store's body never runs, and the old mutate-before-write code passes them. Section 1 had said there was no seam, but `writeJsonAtomic` already accepts `FileOperations` (`write-file-atomic.ts:70`). Fixed in Section 1: an optional `masterFileOperations` constructor argument used by `commitMasterSessions`, plus store tests that fail the rename (EIO, avoiding the EACCES in-place fallback) and assert the cache and disk after add, remove, update and reconcile.

Finding 1 is a confirmed major, so round 4 runs.

## Rounds

### Round 1 (2026-10-31): 4 findings, 4 confirmed

- R1-1 confirmed: the init command was typed as `<cmd>; exit $?` in every
  shell. On Windows the system shell is `cmd.exe` (COMSPEC), where that line
  breaks the command and never exits (5 min timeout); PowerShell exits 1 on
  success. Now picks the syntax by shell. Commit: 5bb5b695.
- R1-2 confirmed: a subtask created with only a description, under a parent
  whose worktree is still pending, got its own worktree via title
  generation, then `syncSubtaskWorktrees` overwrote its path with the
  parent's, orphaning the new worktree and branch. `createWorktreeForTask`
  now skips subtasks. Commit: 5bb5b695.
- R1-3 confirmed: a title with no ASCII letters/digits (e.g. Cyrillic)
  slugified to "" and setup returned silently, leaving the task pending and
  the New Task dialog's agent/flow never started. Falls back to
  `task-<id prefix>`. Commit: 5bb5b695.
- R1-4 confirmed: unstaging a staged rename restored only the new path and
  left the old path's deletion staged. `unstage` now also restores the
  rename source. Commit: 5bb5b695.

### Round 2 (2026-10-31): 3 findings, 3 confirmed

- R2-1 confirmed: a project opened from a repository subfolder got wrong file
  paths. Git status, diff and history paths are relative to the working tree
  root, but every file operation joined them onto the project folder, so
  diffs came back empty, stage/revert/unstage hit the doubled path, and
  `unstage all` only covered the subfolder. `GitService.repoRoot` now
  resolves the root; status uses it for `absolutePath`, and the git handlers
  that take or return file paths run there. Commit: 98aaa026.
- R2-2 confirmed: Commit with Push, and Push then Create PR, ran plain
  `git push`, which Git's default `push.default` refuses on a new
  `task/<slug>` worktree branch (no upstream), so the PR was never created.
  A branch with no upstream is now pushed with `--set-upstream origin HEAD`.
  Commit: 98aaa026.
- R2-3 confirmed: Unstage (file or all) used `git restore --staged`, which
  fails before the first commit (HEAD does not resolve). Now uses
  `git reset -q`. Commit: 98aaa026.


### Round 3 (2026-10-31): 2 findings, 2 confirmed

- R3-1 confirmed: worktree names came only from the title slug, so a second
  task with the same title (or a title matching a kept `task/<slug>` branch
  or a leftover `.worktrees/<slug>` folder) hit `git worktree add -b` on an
  existing branch; setup caught the error, turned the worktree off, and the
  agent started in the main checkout. Setup now appends `-2`, `-3`, … until
  both branch and folder are free. Commit: 9282783c.
- R3-2 confirmed: Revert on the unstaged row of an edited rename (status
  `RM`, row status `modified` with `previousPath`) restored only the new
  path, deleting it and leaving the old path's deletion staged. Revert now
  restores `previousPath` whenever the row carries one. Commit: 9282783c.

### Round 4 (2026-10-31): 2 findings, 2 confirmed

- R4-1 confirmed: a backend stop (app quit, restart) while a worktree task
  was still being set up (title generation or a long init command) left the
  task with `enabled: true, path: null` for good: nothing resumed setup on
  start, and the workspace sat on "Setting up worktree..." forever. Setup now
  records the branch as soon as the worktree exists, and the main backend
  resumes pending setups on start (reruns init in the recorded worktree, or
  creates one). Commit: f41b65d6.
- R4-2 confirmed: the Changes diff for a symlink (e.g. `AGENTS.md ->
  CLAUDE.md`) showed the linked file's contents as the working side; Git
  stores only the target path. A link to a folder failed to load. The
  working side of a symlink is now its target path. Commit: f41b65d6.

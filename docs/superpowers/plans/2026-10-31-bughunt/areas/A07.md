## Already handled

## Rounds

### Round 1 (2026-10-31): 3 findings, 2 confirmed

- R1-1 confirmed: `assertMutableWorkspacePath` resolved the final path
  component with `realpath`, so deleting `docs-link -> docs` in the file
  explorer ran `rm -r` on `docs` (and rename moved the target), leaving the
  link dangling; a link to a folder outside the workspace could not be
  deleted at all. Delete and rename source now use
  `assertMutableWorkspaceEntry` (parent resolved, link kept); writes still
  follow links. Commit: c2243fbd (both).
- R1-2 confirmed: `SettingsStore.update` was an unserialized
  read-modify-write, so overlapping saves (two clients, or the UI and
  Electron's window-close PATCH) both reported success and one patch was
  lost. Updates now run through a `KeyedQueue`, and writes use
  `writeJsonAtomic` so a concurrent `get()` never parses a torn file and
  falls back to defaults.
- R1-3 owner (existing): adopting another data folder keeps ScheduleStore
  and FlowStore on the old folder. Already waiting as A01 R1-2.

### Round 2 (2026-10-31): 2 findings, 1 confirmed

- R2-1 confirmed: startup awaited `ConnectivityService.init()` before the
  server wrote its handshake; on a network that drops the three probes (5 s
  timeout each, sequential) that is ~15 s, past the 10 s deadline of both
  Electron and the TUI, so the app failed to start offline. The probe now
  runs during startup and is awaited only before the scheduler starts;
  `init` goes through `refresh` so an offline result reaches listeners
  registered meanwhile. SIGINT/SIGTERM handlers are now installed before
  that wait, so a quit during the probe still shuts down gracefully.
  Verified with a blackhole proxy: handshake 15.9 s before, 0.9 s after.
  Commit: c889a9f5.
- R2-2 rejected: notification loss between a normal and a dev backend on one
  data folder. Dev-only setup.

### Round 3 (2026-10-31): 2 findings, 2 confirmed

- R3-1 confirmed: settings writes were returned only to the client that
  saved them; no event told other attached clients. The desktop UI keeps
  every machine's settings (`byBackend`) and bakes those cached defaults
  into explicit launch options, which win over the backend's defaults, so a
  second client (another desktop attached to this machine, or this one
  attached to a remote) kept launching agents with the old model or
  account until it reconnected. The backend now broadcasts
  `settings:updated` with the saved settings after every write (WS and
  HTTP); the UI store replaces that machine's copy (layout is not
  re-hydrated), and the TUI settings store follows it, with an epoch so a
  slower load cannot restore older settings. Commit: 1f635998 (both).
- R3-2 confirmed: `NotificationStore.writeAll` used a plain `writeFile`
  while `list()` reads outside the mutation queue, so a UI attaching while
  an agent created a notification could parse a truncated file; the
  initial fetch failed silently and existing notification history stayed
  missing until reconnect. Writes now go through `writeJsonAtomic`.


### Round 4 (2026-10-31): 1 finding, 1 confirmed

- R4-1 confirmed: `SettingsStore.get()` saved a legacy-file migration
  outside the update queue, from the snapshot it had read. On the first
  start after an upgrade, a read that overlapped a save (the backend reads
  settings right after the port handshake, while a client may already be
  saving) could land its migrated old snapshot after the update. The save
  had already been reported and broadcast, but it was gone from disk.
  The migration write now runs on the update queue from a fresh read, and
  `update` reads without migrating, so it cannot wait on itself. A failed
  migration write now returns the migrated settings instead of defaults.
  Reproduced with a test that holds the first read until the update has
  finished. Kept at `round 4` instead of `clear` because it loses a saved
  setting.

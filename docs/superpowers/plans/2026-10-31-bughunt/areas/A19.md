## Rounds

### Round 1 (2026-11-01): 3 findings + 1 found while verifying, 4 confirmed

- R1-1 confirmed: a task branch committed locally but never pushed has no
  upstream, so git status reports `ahead: 0` and the dialog went to PR-only
  mode, calling `GIT_CREATE_PR` for a branch the remote lacks (gh/glab
  fail). `GitStatusResult` now carries `hasUpstream` (from porcelain v2's
  `branch.ab` line; optional, absent from older machines), and PR-only
  pushes an unpublished branch first. f909f29a
- R1-2 confirmed: after commit (and push) succeeded and the request (or the
  push inside `GIT_COMMIT`) failed, the dialog kept its pre-commit mode, so
  a retry tried to commit again ("nothing to commit") and never retried the
  request. A failed submit now rereads status and, when the repository
  moved, reruns the lookup so the dialog offers only the remaining step.
  f909f29a
- R1-3 confirmed: open Changes and History panes fetched once on mount and
  never again, while the header's stats followed agent edits and commits.
  Both now refresh on `GIT_CHANGE_STATS` for their target (new
  `changeTargetId` / `useChangeStatsUpdates` in diff-store, reused by
  TaskHeader); Changes refreshes the shown diff in place, History rereads as
  many commits as are listed and drops a page read superseded by a refresh.
  f909f29a
- R1-4 confirmed (found while verifying): `RemoveProjectDialog` stays
  mounted, so "Keep project data" switched off and cancelled stayed off on
  the next open, defaulting to permanent removal. It resets on open.
  f909f29a
- Side note, root cause outside A19 (backend `change-tracker.ts`,
  `TaskHeader.tsx`): `commitDisabled` is `!hasChanges && ahead === 0`, so a
  plain project (not a worktree task) on a local branch with unpushed commits
  and no upstream gets a disabled Commit/Push button in the header. The new
  `hasUpstream` field makes a fix straightforward; not changed this round.

### Round 2 (2026-11-01): 2 findings + 1 found while verifying, 3 confirmed

- R2-1 confirmed: with "Include unstaged changes" off, a commit and push that
  landed followed by a failed request left status looking as before (the
  unstaged files remain, ahead stays 0), so the R1 recovery saw no change
  and a retry sent `GIT_COMMIT` again ("nothing to commit"), never the
  request. The dialog now remembers that its commit landed and offers the
  request alone, titled with that commit's message. dbf2ff39
- R2-2 confirmed: Fork Project's dialog-wide Enter handler ran on a focused
  Cancel button, so Tab to Cancel + Enter cloned and registered a fork.
  Enter now submits only from the text fields. dbf2ff39
- R2-3 confirmed (found while verifying R2-2): Rename Project had the same
  dialog-wide handler; Enter on Cancel renamed. Same fix. dbf2ff39

### Round 3 (2026-11-01): 2 findings, 2 confirmed

- R3-1 confirmed: a staged-only "Commit & Push" whose commit landed and push
  failed left the unstaged files, so the recovery reread saw changes and
  reopened commit mode with nothing staged: a disabled Commit button and no
  way to retry the push (or the request). The dialog now sends `GIT_COMMIT`
  without push and pushes with `GIT_PUSH`, so it knows the commit landed;
  a failed push leaves it offering Push (and the request) alone. A request
  failing after a push-only push is now offered alone too. 0a3b5557
- R3-2 confirmed: History's refresh asked for every listed commit in one
  `GIT_LOG` read, which the backend clamps to 500, so 600 loaded commits
  dropped to 500 on any repository update. Reads now go in chunks of the new
  shared `GIT_LOG_MAX_LIMIT` (also used by the backend clamp). 0a3b5557

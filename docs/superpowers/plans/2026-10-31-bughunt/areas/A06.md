# A06: taskflow-cli

Status lives in the index table.

## Scope

- packages/backend/src/services/taskflow-cli.sh (macOS/Linux)
- packages/backend/src/services/taskflow-cli-bin.ts (Windows)
- packages/backend/src/services/internal-agent-skill.ts, taskflow-cli-*.md

Test files and test helpers are context, not targets.

## Notes

- Memory `project_dual_cli_implementations`: both implementations must agree; a fix lands in both.
- Memory `project_cli_task_context_bug`: TASKFLOW_TASK_ID fallback must stay.

## Already handled

- POSIX `task create` ignores `--parent` and, in task context, makes a
  top-level task while Windows makes a subtask: owner item A01 R2-1, not a
  bug to fix until the owner picks a behaviour.

## Rounds

### Round 1 (2026-10-31): 6 findings, 6 confirmed

- R1-1 confirmed: Windows `action get/update` and `flow get/update` cast the
  `{actions}`/`{flows}` envelope to an array and crashed (`items.find is not a
  function`). Both CLIs now use new `GET`/`PATCH /api/flows/:id` and
  `/api/flow-actions/:id` routes; the merge happens in `FlowStore` under its
  definitions lock. Commit: cb75c344 (all six).
- R1-2 confirmed: POSIX `flow get/update` (and `action get/update`) split JSON
  on `{`/`}` in awk, so any flow with an action came back truncated and
  updates posted malformed JSON. Fixed by the same routes.
- R1-3 confirmed: POSIX `action update`/`flow update` merged values through a
  `sed` replacement, so `&` became the matched `}` and `/` broke the command.
  The CLIs now send only the changed fields as a PATCH body.
- R1-4 confirmed: POSIX `json_string` left control characters raw, so
  `session input <id> $'\003' --raw` sent invalid JSON (400) and Ctrl-C/Escape
  never reached the session; it also dropped a trailing newline. It now emits
  `\u00XX` and keeps trailing newlines.
- R1-5 confirmed: OpenCode got only a static PROMPT_BASE instruction file;
  task/project scope, flow scope, autonomous mode, project instructions and
  linked projects were dropped. Each launch now gets a content-hashed
  `taskflow-agent-prompt-<hash>.md` with the assembled prompt (written
  atomically by session-lifecycle before spawn).
- R1-6 confirmed: POSIX had no `project move` though the docs advertise it.
  New `POST /api/projects/:id/move` computes the order server-side
  (`computeMovedOrder`); both CLIs call it.

### Round 2 (2026-10-31): 3 findings, 3 confirmed

- R2-1 confirmed: `agent run --model x` without an agent name sent
  `agentOptions: {model}` with no type; with Claude as default agent the
  launch failed (500, "agentOptions must be an object with type claude"),
  with other defaults the model was silently dropped. `POST /api/sessions`
  now stamps the resolved agent type onto untyped options. Commit: cb61366e
  (all three).
- R2-2 confirmed: POSIX `flow start --input` split `key=value` with `cut`,
  which works per line, so a multiline value put its later lines into the
  key and the flow refused to start (missing required input). Now split with
  parameter expansion; a pair with no key is skipped, as on Windows.
- R2-3 confirmed: both CLIs sent `project add <path>` and
  `project update --path` as given, so a relative path (`.`) resolved
  against the backend's working directory, not the caller's. Both now
  resolve it against the caller's directory (POSIX `abs_path`, shared with
  `artifact save`).

### Round 3 (2026-10-31): 3 findings, 3 confirmed

- R3-1 confirmed: `agent run --account work` without an agent name dropped
  the account on both CLIs (sent only for an explicit `claude`/`codex`), so a
  Claude/Codex default agent ran under the project/global account. Both now
  send it when no agent is named; the backend ignores it for agents without
  accounts. Commit: 99462252 (all three).
- R3-2 confirmed: `flow status/stop/pause/resume/skip/jump` used
  `resolve_owner_id`/`resolveOwnerId`, which fail with neither id set, so a
  Master Workspace flow session could not inspect or control its own run.
  They now use the flow owner helpers (`__master__` fallback) like
  `flow complete`/`flow input`.
- R3-3 confirmed (docs): both CLIs treat `--help`/`-h` anywhere as a help
  request, so `attr set <id> "--help"` printed help and exited 0 without
  saving, while the attribute doc promised any flag-looking required
  positional works. The doc now names the exception; changing help detection
  would make `agent run claude --help` launch an agent.

### Round 4 (2026-10-31): 2 findings, 1 confirmed

- R4-1 owner (existing): POSIX `task create` drops `--parent` / the ambient
  task, unlike Windows. Already waiting as A01 R2-1; `--parent` is not in the
  docs, so which behaviour wins is the owner's call.
- R4-2 confirmed: `artifact get <type>` put the label into the URL raw on
  both CLIs, and the JSON route matched it undecoded. A label from an action
  prompt with a space (`code review`) failed on POSIX (curl exit 3) and 404'd
  on Windows; `#`/`?` silently fetched a different artifact (`plan#2` →
  `plan`). Both CLIs now encode the label (POSIX `url_encode`), and the route
  decodes it with the `/raw` route's helper. Commit: 717be9a2. Minor (wrong
  result with a workaround), so the area closes after this round.

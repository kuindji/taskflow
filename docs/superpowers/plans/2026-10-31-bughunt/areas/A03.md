## Rounds

### Round 1 (2026-10-31): 5 findings, 5 confirmed

- R1-1 confirmed: closing a shell session on macOS/Linux sent only SIGTERM,
  which interactive bash and zsh ignore, and dropped the session from the
  map, so the shell kept running with no tab. Reproduced with Bun's PTY.
  The POSIX kill now closes the terminal first (a hangup, as a terminal
  window does), then signals. Commit: 8ecbb7bb.
- R1-2 confirmed: a task deleted or archived while an agent launch waited
  (e.g. on another Codex launch's native-id lock) made saving the session ref
  throw `Task not found` after the PTY had spawned, leaving an agent nothing
  listed or could close, and holding the launch lock. Registration failure
  now closes the PTY and frees the lock. Commit: 8ecbb7bb.
- R1-3 confirmed: on Windows `WindowsPtySession.kill()` cleared `alive`
  before `send()`, which then dropped the kill message; the bridge was
  force-killed 500 ms later and neither exit path called `onExit`, so the
  log, tray entry, SESSION_EXITED and a flow's exit callback were skipped.
  `kill()` now keeps `alive` until the exit arrives. Commit: 8ecbb7bb.
- R1-4 confirmed: renaming a session (WS or `taskflow-cli session rename`)
  saved the label but broadcast nothing, so other clients showed the old
  label. Both handlers now call `sessionLifecycle.renameSession`, which
  patches and broadcasts the owner. Commit: 8ecbb7bb.
- R1-5 confirmed: the HTTP rename route (used by `taskflow-cli`) searched
  only tasks and projects and returned 404 for a master session. Fixed by
  the same shared `renameSession`. Commit: 8ecbb7bb.

### Round 2 (2026-10-31): 3 findings, 3 confirmed

- R2-1 confirmed: a session closed (from another client, or the TUI) while it
  was resuming lost its ref, but the resume then spawned the agent anyway and
  reported success: an agent with no tab or ref, running until it exited.
  Registration now runs on the session's queue, behind the close, and a resume
  whose ref is gone closes the PTY and fails with "Session was closed while it
  was resuming". Commit: 59329765.
- R2-2 confirmed: Kimi native-session discovery read `~/.kimi/sessions` (the old
  Python kimi-cli), but the Kimi Code CLI Taskflow launches writes
  `$KIMI_CODE_HOME` or `~/.kimi-code/sessions/<workspace>/session_<uuid>/`, so
  no Kimi session ever captured an ID and none could be resumed after a
  restart. The old parser would also have read `context.jsonl` as the ID
  "context". Discovery now reads Kimi Code's store and takes the
  `session_<uuid>` directory name, which `kimi --session` accepts. Commit:
  59329765.
- R2-3 confirmed: an agent that exited within milliseconds of spawning (exit
  takes ~4 ms for a failing wrapper) ran its exit cleanup before registration
  had saved the ref, so the cleanup found nothing and registration then saved
  a "live" ref with no process. Fixed by the same queued registration: the
  exit cleanup now runs after it and removes the ref. Commit: 59329765.

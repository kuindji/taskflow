## Rounds

### Round 1 (2026-11-01): 3 findings, 3 confirmed

- R1-1 confirmed: `AgentOptionsPanel` built "off" choices as omitted fields
  (Codex bypass `false || undefined`, OpenCode auto-approve, Pi thinking
  "off" and empty tools, Kimi "manual"), and `normalizeAgentOptions` did the
  same for saved flow inline actions. The backend merges run options over the
  machine defaults, so with Codex "Bypass Safety" on in settings, turning it
  off in Run with options (or in a saved action) still launched with
  `--dangerously-bypass-approvals-and-sandbox`. Non-headless panels now send
  the explicit value. Side effect: an action saved before this opens with
  Save enabled once (same as any stored value differing from the prefill).
  5c37b0f1
- R1-2 confirmed: `ScheduleForm` offered only standalone actions and an
  effect cleared the selection otherwise, so after an action's "Standalone"
  was turned off, opening its schedule and saving any edit sent
  `actionId: null` plus the old custom prompt (the scheduler does not check
  standalone). The schedule's own action stays offered. 5c37b0f1
- R1-3 confirmed: Run now discarded the trigger's rejection (`void
  handleTrigger`), so "Schedule is disabled" (A05 R3-2) and other failures
  showed nothing. The Schedules dialog now shows a dismissible error.
  5c37b0f1

### Round 2 (2026-11-01): 2 findings, 2 confirmed

- R2-1 confirmed: `useRunMenu`'s `navigate` set the active task only when
  the row had one, so running a script, agent command or action from a
  project's Run menu while a task was open left that task's workspace on
  screen (`useActiveWorkspace` prefers the active task) and hid the new
  session. It now clears the active task for project rows. c48d1b62
- R2-2 confirmed: `OpenCodeOptions` used the fixed id `opencode-auto-approve`,
  so with two inline OpenCode actions in a flow, clicking the second one's
  "Disabled" label flipped auto-approve on the first action, which was then
  saved. The id now comes from `useId`, as in `CodexOptions`. c48d1b62

### Round 3 (2026-11-01): 2 findings, 2 confirmed

- R3-1 confirmed: `ScheduleForm` cleared the selected action whenever it was
  missing from the loaded list, so a schedule opened before projects or
  actions arrived (bootstrap, reconnect, slow remote) lost its action for
  good; saving any edit then sent `actionId: null` with the old custom
  prompt the backend still keeps. The action is now derived from the list
  instead of cleared. c3849b40
- R3-2 confirmed: when the selected model does not support the current
  Codex reasoning effort, `CodexOptions` fell back to "Model default", which
  the run panel sends as an omitted field; the backend fills it from the
  machine default, the very level just rejected (e.g. `xhigh`). In session
  mode the fallback is now the model's own default effort, spelled out;
  Settings still falls back to "default". The wider case (choosing "Model
  default" by hand) is owner item A16 R3-2. c3849b40

### Round 4 (2026-11-01): 2 findings, 2 confirmed

- R4-1 confirmed: `FlowPanel` named each row (and its session type) by the
  definition entry at the same position, while rows and Re-run follow the
  run's own order. After the flow was reordered, a finished run's rows showed
  the wrong names and Re-run confirmed one action while the backend reran
  another (it resolves the run's entry id). Entries are now looked up by
  `actionEntryId`. 59824fed
- R4-2 confirmed: `AgentOptionsPanel` prefilled from the raw stored value, so
  a Claude action or schedule saved with the legacy
  `dangerouslySkipPermissions: true` (still honoured by the backend) opened
  on the machine's permission mode and an unrelated edit saved that,
  dropping the bypass. The panel now reads `normalizeAgentOptions(value)`.
  59824fed
- Kept at `round 4`, not cleared: R4-2 silently drops a saved setting on an
  unrelated edit, which the procedure counts as data loss.

### Round 5 (2026-11-01): 2 findings, 2 confirmed

- R5-1 confirmed: the Run menu (native and Radix) hid Flows whenever the
  owner had any run in the store, but a completed or failed run stays there
  for its results panel until the workspace is reopened. So after a flow
  finished, no flow could be started from that workspace. Only a running or
  paused run hides Flows now (`offersFlows`). faa6f2fa
- R5-2 confirmed: offline (no internet) disabled the whole Actions submenu,
  including shell actions, which run locally like the package.json scripts
  that stay enabled. Shell actions now stay runnable offline; agent actions
  are disabled per item (`canRunAction`). faa6f2fa
- Cleared: round 5 found only minor menu-gating bugs with workarounds
  (reopen the workspace; type the command in a terminal).

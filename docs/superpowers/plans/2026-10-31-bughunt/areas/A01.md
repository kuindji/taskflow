## Rounds

### Round 1 (2026-10-31): 2 findings, 2 confirmed

- R1-1 confirmed: `PATCH /api/tasks/:id/worktree` (`taskflow-cli task worktree --disable`) on a subtask force-removed the parent's shared worktree and branch. Subtasks now get 400. Commit: c603c9c2.
- R1-2 confirmed in part: changing the data folder did not move `session-logs/` or `sessions/` (Master list), so terminal history and Master sessions vanished; the move also took `agent-skills` out of the base dir, and the task store was re-pointed without `masterSessionsFile`. Fixed in the same commit. The rest (flows, flow-runs, schedules, notifications) needs their stores re-pointed live: owner item.

### Round 2 (2026-10-31): 2 findings, 2 confirmed

- R2-1 confirmed: `POST /api/projects/:id/tasks` dropped `parentId`, so the Windows CLI's `task create` (subtask in task context, or `--parent`) made a top-level task off the parent's worktree. The route now validates the parent through the shared `TaskStore.getSubtaskParent` (also used by the WS handler) and inherits its project and worktree. Commit: 99d0004a.
- R2-2 confirmed: `PATCH /api/tasks/:id/worktree --disable` on a parent removed the shared worktree but left subtasks (active and archived) with `enabled: true` and the deleted path, so new sessions there failed to start. Subtasks now get the parent's new worktree state. Commit: 99d0004a.

### Round 3 (2026-10-31): 2 findings, 2 confirmed

- R3-1 confirmed: `DELETE /api/tasks/:id` (`taskflow-cli task delete`) broadcast nothing, so the task (and its subtasks) stayed in the desktop UI and TUI until a reload. The route now broadcasts a new `task:deleted` event with `{ id }`; the UI and TUI drop the task family on it. WS handlers still do not broadcast their own mutations (the requesting client applies the response), as before. Commit: 600186bb.
- R3-2 confirmed: restoring a subtask whose parent is still archived (UI archive view, TUI, or `taskflow-cli task unarchive`) made the subtask active under an archived parent, so it showed in neither list. `TaskStore.unarchiveTask` now refuses with a `ConflictError` (HTTP 409, WS error); the UI shows "Could not restore task" instead of failing silently. Commit: 600186bb.

### Round 4 (2026-10-31): 2 findings, 2 confirmed

- R4-1 confirmed (data loss): changing the data folder (Settings, Overwrite) to a folder that overlaps the current one deleted the data before moving it. Moving a data folder named like a data item (`…/X/tasks`) to its parent `…/X` cleared the destination `X/tasks`, which was the whole current folder; the same folder under another spelling (`X/`) deleted `projects.json`. `migrateDataDir` now resolves both folders and refuses an overlapping move before touching anything. Commit: e77932db.
- R4-2 confirmed: a subtask added while its parent's worktree was still pending (title generation or init command running) copied `{ enabled: true, path: null }` and never got the finished worktree, so its sessions ran in the main checkout. Worktree setup now passes the finished (or failed, disabled) worktree to the subtasks, through a new shared `TaskStore.syncSubtaskWorktrees` that the worktree-disable route also uses now. Commit: e77932db.

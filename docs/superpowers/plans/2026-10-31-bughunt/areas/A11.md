## Rounds

### Round 1 (2026-11-01): 3 findings, 3 confirmed

- R1-1 confirmed: `before-quit` stopped the backend before any window `close`
  handler sent the window-bounds PATCH, so Quit/tray Exit with the window open
  lost the bounds. Quit now saves first and waits. 6ffb4505
- R1-2 confirmed: `showMainWindow` during `createWindow`'s settings fetch (a
  dock click while the backend starts or is busy) built a second window; the
  first `closed` then nulled the shared reference. Creation is shared, `closed`
  checks identity, `activate` waits for the backend. 6ffb4505
- R1-3 confirmed: a notification click with the macOS window closed did
  nothing. It now reopens the window and the new renderer takes the click via
  `take-pending-notification-click` when it subscribes. 6ffb4505

### Round 2 (2026-11-01): 2 findings, 2 confirmed

- R2-1 confirmed: `second-instance` during startup called `showMainWindow`
  with no backend port, so the window loaded, its first connect failed and
  nothing retried. `showMainWindow` now leaves opening to `whenReady` until
  the port is known (the `activate` guard moved there). 21d1aea1
- R2-2 confirmed: a macOS staging error that arrives after the download
  promise settled failed the download but never released the operation, so
  Retry and Check did nothing until restart. `fail` now releases settled
  operations. 21d1aea1

### Round 3 (2026-11-01): 1 finding, 1 confirmed

- R3-1 confirmed: a notification's click resolved its machine only by the
  tunnel origin it was shown from, and a reconnect gives the tunnel a new
  local port, so clicking it after an SSH drop and reconnect opened the window
  without navigating. The click now prefers the id it was shown under while
  that id is attached, falling back to the origin for a handshake rename.
  82e2c532

### Round 4 (2026-11-01): 2 findings, 2 confirmed

- R4-1 confirmed: the notification poller keyed its watermark by tunnel
  origin and dropped it when the tunnel exited, so after an SSH drop and
  reconnect (new local port) the first poll set a fresh cutoff and every
  notification raised during the outage was never shown. A dropped machine
  the user still wants attached now parks its watermark by id and the new
  origin resumes from it; a deliberate detach still starts afresh. eb6c9b10
- R4-2 confirmed: a window reopened maximized read its "normal" bounds after
  `maximize()`, which on Windows/Linux are the screen's, so quitting while
  still maximized saved them and the next restore came back screen-sized.
  Normal bounds are now read before maximizing. eb6c9b10

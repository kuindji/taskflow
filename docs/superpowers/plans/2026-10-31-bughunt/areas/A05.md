## Rounds

### Round 1 (2026-10-31): 3 findings, 3 confirmed

- R1-1 confirmed: a run keeps the step list it started with, but each step
  was launched from the definition by position. Removing a later step while
  the flow ran left the next step `running` with no session (the launch
  returned silently), and reordering steps launched the wrong one. Steps are
  now looked up by entry id; a removed step fails and pauses the run, so the
  user can skip it. Commit: 9bf7c87d.
- R1-2 confirmed: `flow jump` on an ended run reopened it even while another
  flow was active on the same owner, so two flows ran at once and the UI
  (one active run per owner) showed only one. Jump now applies the same
  one-active-flow check as start. Commit: 9bf7c87d.
- R1-3 confirmed: deleting a schedule (CLI or another client) broadcast
  nothing, so open UI and TUI schedule lists kept the row until reopened. The
  scheduler now broadcasts `schedule:deleted`; both stores drop the row, and
  the TUI store also drops it from a list load already in flight.
  Commit: 9bf7c87d.

### Round 2 (2026-10-31): 3 findings, 3 confirmed

- R2-1 confirmed: a session that exited while its launch was still
  registering it (flows: the lifecycle persists the session ref after
  spawning the PTY; schedules: the run is recorded after spawn) had its exit
  dropped, so the flow step stayed `running` with a dead session and the
  schedule refused triggers as "already running" until its timeout (forever
  with timeout 0). Both runners now hold such exits and replay them once the
  run records the session; the scheduler matches exits to runs in memory.
  Commit: c85694a0.
- R2-2 confirmed: `rate(0 minutes)` passed validation, so a schedule was due
  again the moment it finished, and a failing spawn retried in a tight loop.
  Rates below 1 are rejected. Commit: c85694a0.
- R2-3 confirmed (low): a pre-0.14 run file at `flow-runs/<owner>--<flow>.json`
  left `running`/`paused` after its `flow-runs/main/` record ended blocked
  deleting the flow forever ("has active runs"). Deletion now lets the main
  instance's record supersede the legacy one, as `getFlowRun` does.
  Commit: c85694a0.

### Round 3 (2026-10-31): 3 findings, 3 confirmed

- R3-1 confirmed: deleting an action checked only flows, so an action used by
  a schedule could be deleted; the schedule then fell back to its own
  (usually empty) prompt and the default agent, launching a session nobody
  asked for. WS and HTTP deletion now refuse an action a schedule runs, and a
  schedule whose action is missing fails its run with "Action not found"
  instead. Commit: d8e70acd.
- R3-2 confirmed: "Run now" / `schedule trigger` on a disabled schedule
  returned success and launched nothing. It now rejects with "Schedule is
  disabled". Owner question logged: should a manual run start a disabled
  schedule once instead? Commit: d8e70acd.
- R3-3 confirmed: schedule create (WS and HTTP) answered with the record from
  before it was armed (`nextRunAt: null`), and the UI and TUI stores overwrote
  the broadcast record with it, hiding the next run time until a reload. Both
  now return the stored record. Commit: d8e70acd.

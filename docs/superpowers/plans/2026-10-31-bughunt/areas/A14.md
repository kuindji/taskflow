# A14: UI tasks, projects, sidebar

Status lives in the index table.

## Scope

- packages/ui/src/stores/task-store.ts, project-store.ts, task-creation-store.ts
- packages/ui/src/components/sidebar/ (except files listed under A12, A17)
- packages/ui/src/lib/dropped-task.ts, project-visibility.ts
- packages/ui/src/components/panels/TaskInfoPanel.tsx, AttributesSection.tsx, LinkedProjectsSection.tsx, ProjectAgentAccountsSection.tsx, EditedFilesList.tsx

Test files and test helpers are context, not targets.

## Notes

- none

## Already handled

- Archiving a task within the 400 ms autosave window loses the pending
  Task Info edit (R2-2): archive is only reachable through a context menu or
  a confirm dialog, which takes longer than the debounce.

## Rounds

### Round 1 (2026-11-01): 4 findings, 4 confirmed

- R1-1 confirmed: an archive or restore made elsewhere (`taskflow-cli task
  archive`/`unarchive`, HTTP routes broadcast `TASK_UPDATED`) only replaced
  the record in place, so an archived task stayed in the live sidebar and a
  restored one never came back. The event now moves the task family between
  lists by status. f291197c
- R1-2 confirmed: a subtask archived on its own (parent still active) was
  nested under its absent parent in the archive view and could not be seen,
  restored or deleted. A subtask whose parent is not listed now gets its own
  row (`task-groups.ts`). f291197c
- R1-3 confirmed: creating a second worktree task with "Start immediately
  with" an agent or flow before the first one's worktree (and init command)
  was ready replaced the first one's pending start, so it never started.
  Pending starts are now kept per task. f291197c
- R1-4 confirmed: the Linked Projects picker offered projects from every
  attached machine; a link to another machine's project is saved but never
  resolved by the owning backend, so agents silently got no link. The picker
  now lists only projects on the owning project's machine. f291197c

### Round 2 (2026-11-01): 3 findings, 2 confirmed

- R2-1 confirmed: a Task Info / Project Info autosave that failed (the
  record's machine offline, or the backend refusing it) still moved the saved
  baseline to the unsaved text, so neither the next edit nor the flush on
  switching away sent it again and the edit was lost. A failed save now hands
  its fields back to the dirty set. be4b514b
- R2-2 rejected: archive during the 400 ms debounce drops the pending edit;
  archive needs a context menu or confirm dialog, slower than the debounce.
- R2-3 confirmed: "Add subtask" from a task card that is not the selected
  task opened the dialog on the selected task's (or project's) project, so
  agent availability and agent options came from the wrong project and
  machine. The request now carries the parent's project. be4b514b

### Round 3 (2026-11-01): 3 findings, 3 confirmed

- R3-1 confirmed: Linked Projects add and remove wait for the backend reply
  before the section's link list moves, so a note save sent meanwhile used
  the old list: closing Project Info right after removing a link with a note
  restored the link, and editing a note while an added link was in flight
  dropped the added link. Add and remove now move the list ahead of the
  reply. b3f23a80
- R3-2 confirmed: `taskflow-cli project add` on an archived project's path
  restores that record and broadcasts `PROJECT_CREATED`, but the UI ignored
  the event for a known id, so the project stayed archived until a refresh.
  The event now replaces a known record. b3f23a80
- R3-3 confirmed: sidebar keyboard navigation (Cmd+arrows, Cmd+1–9) walked
  the live task list in the archive view, selecting tasks that were not
  shown and skipping archived rows. It now walks the shown rows (including a
  subtask archived alone), and the task number badges count the same rows.
  b3f23a80

### Round 4 (2026-11-01): 3 findings, 3 confirmed

- R4-1 confirmed: Linked Projects note drafts were set only when the
  project changed, so a note edited elsewhere (TUI, another client, HTTP
  API) stayed stale in the panel and the next note edit wrote the old note
  back. A note changed in the record now replaces its draft unless that
  draft has an unsaved edit. 2e7348a0
- R4-2 confirmed: New Task with "Start immediately with → Flow" on a flow
  that has inputs started it without input values, so the backend refused it
  ("Missing required flow input") and nothing ran. The flow's input dialog
  now opens after the task is created; a worktree task keeps the values for
  its deferred start. 2e7348a0
- R4-3 confirmed: the Electron native context menu of a task or project was
  built before its package scripts and agent commands were fetched, so the
  first opening never listed them. The native menu now reads them (3 s cap)
  before it is shown. 2e7348a0

### Round 5 (2026-11-01): 3 findings, 3 confirmed

- R5-1 confirmed: Task Info and Project Info drafts were set only when the
  record changed identity, so a title, description or notes edited elsewhere
  (an agent's `taskflow-cli task update --notes`, the TUI, another client)
  stayed stale in the panel and the next edit of that field wrote the old
  text back. A changed field now replaces its draft unless the draft has an
  unsaved edit. 9c282654
- R5-2 confirmed: New Task reset and closed the dialog before the create
  request settled, so a create that failed (the project's machine offline)
  dropped the typed description with only a console error. The dialog now
  waits for the create, and a failure keeps the form open with the error.
  9c282654
- R5-3 confirmed: a task list refresh with the archive view open refetched
  the archive only for a machine that had no archive slice yet, so after a
  reconnect a task archived or restored while away stayed wrong in the
  archive view (a restored task listed in both). Every refresh now refetches
  the shown archive. 9c282654

### Round 6 (2026-11-01): 3 findings, 3 confirmed

- R6-1 confirmed: a Linked Projects note save did not move the section's
  link list, so removing (or adding) a link before that save's reply sent the
  old note with the new list, and the backend's whole-list replace reverted
  the note. Every save now moves the list ahead of its reply. cc7b56bb
- R6-2 confirmed: New Task deferred "Start immediately with" only for a
  top-level worktree task, so a subtask created while its parent's worktree
  was still being set up started its agent or flow in the main checkout. The
  start now waits whenever the created task's worktree has no path yet.
  cc7b56bb
- R6-3 confirmed (regression from R5-2): a create still in flight when New
  Task was cancelled closed and cleared the dialog reopened meanwhile once it
  settled, losing the new draft. Closing the dialog now detaches the pending
  create from the form. cc7b56bb

### Round 7 (2026-11-01): 2 findings, 2 confirmed

- R7-1 confirmed: a Linked Projects note save that failed (the project's
  machine offline, the backend refusing it) still moved the saved baseline
  to the new note, so neither the next edit nor the flush on closing Project
  Info sent it again and the note was lost. A failed save now hands its notes
  back to the dirty set (the R2-1 helper, moved to `lib/draft-baseline.ts`).
  10c2d2c9
- R7-2 confirmed: an attribute value (or name) changed back to its stored
  text while the save of the other text was still in flight was skipped as a
  no-op, so the in-flight save won and the field ended on the text the user
  had undone. The no-op check now compares against the latest in-flight save
  or the latest rendered attribute. 10c2d2c9

### Round 8 (2026-11-01): 2 findings, 2 confirmed

- R8-1 confirmed: when two Linked Projects note saves were in flight, the
  older one's reply passed the "clean draft" check (the baseline had already
  moved to the newer note), so the note on screen went back to the older
  text, and closing Project Info after editing another link's note sent the
  whole list with the older note, overwriting the newer one. Task Info and
  Project Info fields had the same revert on screen. A reply that matches an
  older pending save but not the latest is now skipped (`trackSave` and
  `isStaleReply` in `lib/draft-baseline.ts`). 2c5e9f5a
- R8-2 confirmed: Edited Files put the working directory in front of every
  logged path, so a file logged with an absolute path (one in a linked
  project, outside the task's checkout, which the backend keeps absolute)
  opened at `<workingDir>//abs/path`. An absolute path now opens as logged.
  2c5e9f5a

### Round 9 (2026-11-01): 2 findings, 2 confirmed

- R9-1 confirmed: New Task's Agent Options panel was not handed the form's
  options, so collapsing and reopening it (which remounts it) showed the
  machine defaults while the form still submitted the earlier picks (for
  example Bypass Permissions shown as Inherit). The panel now opens on the
  form's options. 39ad2d03
- R9-2 confirmed: changing the New Task project to one on a machine without
  the chosen agent kept the agent selected ("not installed") and Create Task
  started it there, which failed with only a console error. An agent the
  project's machine lacks now counts as "Don't start", as a flow out of reach
  already did. 39ad2d03

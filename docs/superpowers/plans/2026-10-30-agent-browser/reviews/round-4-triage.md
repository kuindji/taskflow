# Round 4 triage

Source: `round-4.md` (gpt-6.1-sol, read-only, against 84c0815b). Checked against Puppeteer 23.6 `ChromeTargetManager.ts`, Chromium 130 `target_handler.cc` and `browser_devtools_agent_host.cc`, Electron v33.4.11 `guest-window-manager.ts` and `api/web-contents.ts`, the installed `electron.d.ts`, and the repo.

Part A (round-3 fixes): agreed. The two "not fully" rows are findings 2 and 3.

1. **confirmed, blocker.** Puppeteer's `initialize()` (`ChromeTargetManager.ts:141-160`) auto-attaches at browser level with `filter: [{type:"page", exclude:true}, {}]`, so it attaches to **tab** targets and reaches pages only through each tab session's own `setAutoAttach` (`:401-406`). Chromium 130 creates tab targets in the content layer (`browser_devtools_agent_host.cc:143` auto-attaches `kTypeTab`; `target_handler.cc:1005-1011` refuses a filter allowing both tab and page). A tab target's id isn't the page's, so `resolveTarget` times out, the filter detaches it, and Puppeteer never sees the page (its init waits on the discovered pages). Playwright is unaffected: its auto-attach uses Chromium's default filter, which excludes tabs. Fix (simpler than Codex's registry change): the filter learns target types from upstream events, and a `tab` target is decided by its page. A new `CdpFilterDeps.pageOfTabTarget` resolves it through a **separate** short-lived upstream connection (attach to the tab, auto-attach once, read the page's targetId, detach). It can't use the client's upstream: that stream is processed strictly in order while the attach waits, so it would deadlock. Commands naming a tab id are translated to its page. Pages under an allowed tab session already pass as nested attaches. Spike records the tab hierarchy and confirms the resolution method; filter tests cover it; Section 8 already runs Puppeteer.
2. **confirmed, major.** `web-contents.ts:752` runs the open handler on `-will-add-new-contents`, and `:805-821` runs `openGuestWindow` on `-add-new-contents`, a later task (Chromium's `ShowCreatedWindow`). `guest-window-manager.ts` navigates an existing named popup before `createWindow`, and only registers names after creation (`handleWindowLifecycleEvents`). Two families can both pass the check while the name is free. Fix: `mayOpenNamed` becomes `claimPopupName`, which reserves the name for the family on success. `reportChildOpened` keeps it; the reservation is released when that family's root closes. A reservation that's never used blocks other families only until then.
3. **confirmed, minor (Codex: major).** Real: Section 2's `close` propagates a `store.remove` failure, the route answers 500, and the link drops the `closed` event, so a saved root can come back after restart. It only happens when the atomic write fails (disk full, permissions), so it's minor. Fix: `close` clears runtime state and fires tab-gone for every tab even when a store write fails, then rethrows; a `closed` event for an id the registry no longer holds still calls `store.remove(id)`, so a retry is idempotent; the link retries a 5xx up to 3 attempts in total, then drops it. A 4xx is dropped at once.
4. **confirmed, major.** `app-menu.ts:269-270` exposes reload and force reload. The views are main-owned children of the window's `contentView`; a reload runs no React cleanup, the session store starts empty (`session-store.ts:157-158`), and the first registry sync activates nothing (`06-ui.md`), so nothing hides an attached view and it covers the rebuilt UI. Fix: main calls `tabHost.detachAll()` on the main window's `did-start-navigation` for a main-frame, cross-document navigation, and on `render-process-gone` (`WebContentsDidStartNavigationEventParams` has `isMainFrame`/`isSameDocument`, checked in 33.4.11 typings). Views stay alive; the new renderer shows its active panes. Review Focus 3 and Section 8 updated.

Outcome: one blocker and two majors confirmed in round 4, the cap. Fixes folded in; the chain stops for the user.

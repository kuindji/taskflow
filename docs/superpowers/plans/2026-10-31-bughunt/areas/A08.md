## Rounds

### Round 1 (2026-10-31): 5 findings, 5 confirmed

- R1-1 confirmed: "Replace this match" applied the search's saved column to
  the current file, so replacing the first `foo` in `foo foo tail` and then
  the second wrote `x foxail`. The backend now refuses coordinates whose
  line no longer equals the match's `lineContent` (count 0), and the UI
  shifts the remaining matches on the replaced line and keeps a refused one
  with an error. Found while verifying: on line 1 of a file with a UTF-8 BOM
  rg counts columns after the BOM, so the replace also ate the BOM and a
  character; the BOM is now stripped for the edit and written back.
- R1-2 confirmed: whole-word regex replace built `\bfoo|bar\b`, so replace
  all changed `foo` inside `foobar`, text the search never listed. The
  pattern is now grouped.
- R1-3 confirmed: without the regex option rg still parsed the query as a
  regex (`a.b` matched `axb`, `[` returned nothing). Literal mode now passes
  `--fixed-strings`.
- R1-4 confirmed, worse than reported: a match on a line that is not UTF-8
  comes back as `lines.bytes`; the parser read `lines.text.replace` inside
  the child's `close` listener, and in Bun that uncaught throw exits the
  backend (checked). Bytes are decoded now; non-UTF-8 paths are skipped. As
  a consequence replace could now reach such files, and decoding them as
  UTF-8 and writing back would turn every invalid byte into U+FFFD, so
  replace leaves files that are not valid UTF-8 untouched.
- R1-5 confirmed: backlinks lived in a plain object, so a link to a page
  named `constructor` threw in graph construction and the wiki failed to
  load; a page named `toString` was never an orphan. Backlinks are built in
  a Map. Side note for A20: `WikiRail.tsx` reads `index.backlinks[pageId]`
  on the parsed JSON object, so a `toString` page with no backlinks still
  gets the prototype function there.

Commit: b412bc24 (all five).

### Round 2 (2026-10-31): 3 findings, 3 confirmed

- R2-1 confirmed: the editor (and the markdown pane's checkbox toggle) got a
  file that is not UTF-8 decoded with every invalid byte as U+FFFD, and
  saving wrote that back, so editing one word in a Latin-1 file destroyed
  all its accented characters. `FILE_WRITE` now refuses to overwrite an
  existing file that is not valid UTF-8. Side note for A18: the editor
  still opens such a file as editable and its save handler only logs the
  refusal (the dirty marker stays); opening it read-only needs `FILE_READ`
  to say the content was decoded lossily.
- R2-2 confirmed: replace all re-matched each file with a JS regex, whose
  `\b` is ASCII-only and differs from rg's `--word-regexp`, so whole-word
  `C++` replaced the `C++` in `C++x` and skipped the listed one, and `foo`
  replaced `fooé`. Replace all now splices at the matches its own rg run
  reported; in regex mode a sticky JS regex at that column expands `$1`,
  and a match JS does not see there is skipped.
- R2-3 confirmed: literal replace all passed the replacement to
  `String.replace`, so `$&` reinserted the match. Literal mode now inserts
  the replacement as typed. Side note for A18: "Replace this match" also
  inserts it as typed in regex mode (no `$1` expansion), unlike replace
  all; expanding it needs the response to return the inserted text,
  because `shiftAfterReplace` shifts by the typed replacement's length.

Commit: a37b937f (all three).


### Round 3 (2026-10-31): 3 findings, 3 confirmed

- R3-1 confirmed: the round 2 fix for regex replace all re-ran a sticky JS
  regex at rg's column and skipped the match when JS's length differed, so
  replace all silently left `foobar` unchanged for whole-word `foo|foobar`
  (JS takes the first alternative), `café` for `\w+` (JS `\w` is ASCII) and
  an emoji for `.` (JS matches one UTF-16 unit), while reporting success. A
  replacement without `$` is now inserted at rg's span as is; with `$`, a
  JS mismatch is retried with the match forced to end where rg's ended.
- R3-2 confirmed: the TypeScript resolver cached every parsed tsconfig (and
  every "no tsconfig here") until the backend restarted, so after changing a
  `paths` alias Cmd-click on an import still opened the old target, and a
  tsconfig added later was never found. The caches are gone; parsing skips
  `include` globbing so a read per request stays cheap.
- R3-3 confirmed: wiki link extraction blanked fenced code but not inline
  code, so `` `[[target]]` `` written as an example became a backlink
  (target no longer an orphan) and `` `[x](missing.md)` `` a broken link,
  while the renderer leaves both unlinked. Inline code spans are blanked too.

Commit: 3ea0bbee (all three).
